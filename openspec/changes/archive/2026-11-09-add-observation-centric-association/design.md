# Design

## Context

前置 `add-ebike-tracking-core` 提供固定帧率的预测框、单帧检测、轨迹池和时延基准。主匹配在进入此变更前应已通过合成回放。方案按 [OC-SORT](https://arxiv.org/html/2203.14360) 中 OCM 与 OCR 的职责实现，比较时标明本项目沿用的 XYAH 状态和轨迹生命周期。

## Goals / Non-Goals

- **Goals** 将真实观测方向和最近实测位置加入现有匹配，不增加当帧滤波更新次数。
- **Non-Goals** 本变更的恢复范围为短时、几何可辨的轨迹重现。ReID、低分救援与滤波回放各有独立成本和验证边界。

## Decisions

1. **OCM 先计算代价再分配。** 只使用最近有效真实检测框中心及更早的参考点，方向为从参考点到最近点，候选方向为从同一参考点到候选点。先筛选可行 IoU 配对，再计算方向代价，并将其作为几何代价的软项。按轨迹复用参考方向，历史过旧、位移不足、向量无效时将方向项置零。保留固定权重基线，以及按位移和有限历史方向稳定性调权的实验配置。急转时旧方向仅作为辅助，不能替代几何门控。
2. **OCR 只处理主匹配剩余候选。** 对窗口内未匹配的已确认或丢失轨迹，用最近一次实测框和剩余有效检测做一次几何门控与分配。窗口不得超过主链路存活期。容量不足时优先保留更近期实测的轨迹，按 ID 打破平局，检测侧按分数和原检测顺序取舍。通过主关联的结果不重算。使用最近真实框可以避免漂移预测的影响，同时需要时间门控降低旧位置误连风险。
3. **把控制状态留给轨迹池。** 关联阶段返回匹配对、来源及未匹配集合，统一在关联结束后更新状态和观测历史。保留常数上限的真实观测缓冲，与未来 ORU 虚拟点隔离。关闭 OCM/OCR 时走原匹配路径，避免生成方向矩阵和第二轮候选。
4. **计量增量。** 沿用主链路预算，分别记录两种功能的开关组合、OCM 有效方向数、OCR 输入行列、运行与跳过次数。除普通缓存外，构造主关联大量失配的密集片段。用相同数据做前后对照，避免只比较平均 FPS。

## Risks / Trade-offs

- 停车和极短位移时，框抖动可能使方向翻转。使用位移、观测间隔和历史新鲜度控制有效性。适配更复杂的方向模型留待实测。
- 两辆车在相同地点交叉，最近框可能错误抢占检测。短窗口、类别和几何门控之外保留未匹配选项，并按遮挡事件记录错误重连。
- OCR 的最坏负载可能接近额外一轮分配。对剩余输入设置独立上限，空候选时短路，超限及其质量影响写入报告。

## Migration Plan

先保留主链路配置，再逐一开启 OCM 与 OCR 作对照。实现和合成检查通过后，可继续实现 ORU。目标环境的精度与时延证据另行补齐，未达预算时采用已验收的开关组合。
