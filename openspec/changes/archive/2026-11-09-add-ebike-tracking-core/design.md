# Design

## Context

当前 `inference_ebike.py` 调用 `model.predict`，其 `Results.boxes` 提供还原到原图的检测框。仓库的 `model.track()` 注册 ByteTrack 和 BoT-SORT。项目跟踪层从现有检测结果接入，并提供单独的回放入口。见 [proposal.md](proposal.md)。

## Goals / Non-Goals

- **Goals** 提供固定帧率下可用的最小跟踪器、稳定的逐帧接口和后续变更可重跑的基准。
- **Non-Goals** 本阶段的适用范围为单路固定帧率、连续解码的电动自行车视频。可变帧率、跳帧、跨流共享 ID 和地面标定在独立变更中评估。

## Decisions

1. **分离视频适配与轨迹核心。** 以独立 `track_ebike.py` 串联逐帧读取、检测与跟踪。缓存回放与视频推理调用同一个 `Tracker.update`。相对于在 `model.track()` 注册回调，这能直接回放检测框并测量不含模型的纯跟踪时延。缓存用带版本、来源和 FPS 元数据的 JSONL，一帧一行。帧号从 0 起连续，时间戳用视频时间（秒），原图尺寸用于检测坐标校验；缓存记录类别、置信度和原图像素 `xyxy`。无框帧显式记录空数组。只有带框视频时，需要原始视频与权重重新推理，或提供结构化框和分数。导出统一框数据时，每帧集中做一次必要的张量转 CPU，避免逐框同步。
2. **复用固定步长滤波器。** 采用仓库 `KalmanFilterXYAH`，其 `dt=1` 对应一个处理帧，位置与高度用像素，速度按帧计，长宽比无单位。输入校验先拒绝非有限、退化框和不在 `[0,1]` 的分数。输出中区分滤波框和匹配检测索引，索引指向候选过滤前的该帧记录。ID 由单个视频的轨迹池分配，重复回放时对同分候选与输出排序使用稳定顺序。
3. **让不可行配对在求解前退出。** 主匹配用预测框 IoU 和类别门控，先匹配已确认与可找回轨迹，再处理剩余检测与待确认轨迹。用项目已有 SciPy 依赖实现支持未匹配项的线性分配，可用有限代价和虚拟未匹配项，禁止把不合格边当作有效匹配。只在完整分配后删掉坏边，可能吞掉原本可接受的匹配。两轮共享候选容量，每个真实检测最多消费一次。达到容量时先按分数和原检测顺序截断候选，既有轨迹保留，初始化请求超过剩余槽位时跳过并计数。到期判定采用当前帧号减最近实测帧号，超过配置才移除。
4. **统一时延口径。** 跟踪计时从内存中当帧检测就绪到结构化轨迹产生。端到端测量从帧到达处理入口到轨迹就绪，含排队等待、解码、检测与适配，渲染、编码、落盘单列。以目标帧率节奏持续供帧，并记录超期和待处理量，以免同步回放掩盖处理欠账。用单调墙钟，统一预热、采样区间和重复次数，记录设备、线程、软件环境、分辨率、权重、输入清单、候选规模和阈值。缓存基准覆盖普通、密集与容量截断，比较时不得通过丢帧或改变输入来压低延迟。
5. **先留出检测预算。** 目标设备和 FPS 等真实视频提供后固定。暂定跟踪 P95 预算为目标帧周期的 20%，端到端 P95 不超过一个目标帧周期，持续负载下吞吐达到目标帧率且无持续积压或跳帧。以 30 FPS 为例，暂定预算分别约 6.7 ms 与 33.3 ms。20% 是本方案的建议预算，可在部署验证前按目标环境重新登记。P99 单列，用于识别偶发尖峰。本地合成测量用于发现回归，自动测试断言工作量上限和输出，不依赖机器速度。

## Risks / Trade-offs

- 密集帧的候选矩阵及分配代价随输入规模增大。先门控、限制行列数、空侧时跳过计算，并报告截断及恢复质量。
- 长视频缓存、同步写盘、渲染及逐框设备同步会增大内存或尾延迟。逐帧消费，默认关闭渲染与逐帧调试日志，按需写出结果，基准单列输出开销。
- 固定步长对缺帧或可变帧率存在时间误差。首版明确检查帧序和时基，空检测作为正常帧；不能确认帧对应关系时拒绝该输入。
- 容量过低可能降低召回。验证报告须带输入数和截断数，真实密集片段用于选定容量。

## Migration Plan

通过独立入口启用本项目跟踪器。首次用合成缓存跑通并保留基线配置和报告，再用真实视频与第一部分权重或缓存重跑。后续变更以该基线作对照，复用相同输入和计时边界。
